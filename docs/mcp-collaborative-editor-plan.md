# MCP-редактор коллаборативных документов

Статус на 10 ноября 2026 года: реализованы MVP ядра ops-слоя, адаптер handles живых Yjs-контейнеров и проверка удаления по отпечатку поддерева. Подключение RPC, прав, сохранения Hocuspocus и MCP остаётся работой фаз 1–2.

## Цель и границы

Создать общий движок адресного редактирования одного поля коллаборативного документа через существующий REST RPC коллаборатора. MCP предоставляет агенту чтение, описание схемы и пакет правок. Движок работает с актуальным документом в Hocuspocus и использует публичные библиотеки Tiptap/ProseMirror/Yjs; платный AI Toolkit не требуется.

Правила конкретных приложений, например жизненный цикл QMS, остаются у вызывающего приложения. В этой работе не создаём отдельные адаптеры QMS или обычных документов.

В MVP входят прямые правки, вставка и удаление узлов, изменение разрешённых атрибутов, замена текста, применение и снятие обычных marks. Не входят перемещение узлов, предложения с accept/reject, полная замена документа, глобальная проверка версии и гарантированный повтор записи после сбоя.

## Принятые решения

| Вопрос | Решение |
| --- | --- |
| Публичная адресация | Непрозрачный handle конкретного живого контейнера документа и поля |
| Зависимость ссылок от CRDT | Внутри адаптера используется идентичность Yjs; MCP не получает отдельные поля client/clock |
| Изменения ради MCP | Нет новых атрибутов, миграции или записи при чтении |
| UUID редактора | Для адресации MCP не используется и не генерируется; существующие атрибуты сохраняются согласно схеме |
| Текстовые узлы | Не получают UUID; текст адресуется внутри узла-контейнера |
| Устаревшее состояние | Общего запрета по ревизии нет; потеря контейнера или изменение удаляемого поддерева требует нового чтения |
| Проверка удаления | Обязательный expectedFingerprint всего поддерева, проверяемый на начальном снимке batch |
| Срок жизни handle | Переживает бинарную загрузку Yjs; пересоздание контейнера или документа из JSON инвалидирует ссылку |
| Применение | Сразу в документ, после проверки всего пакета |
| Неопределённый результат записи | Перечитать документ; автоматически запрос не повторять |
| Перемещение | После MVP и отдельной проверки конкурентного редактирования |

## Существующая точка интеграции

Расширяем `/rpc/:id` и `collaborator-client`. Сохраняем существующее кодирование адреса документа: workspace, object class, object ID и attribute. Один пакет правок относится к одному документу и одному полю.

Поток выполнения:

```text
MCP tool → collaborator-client → существующий RPC
                              → проверка доступа текущего запроса
                              → движок схемы и операций
                              → живой документ Hocuspocus
                              → существующее сохранение
```

MCP не хранит вторую копию редактора и не реализует собственные правила преобразования документа. Общие wire-типы не зависят от экземпляров Tiptap Editor. MCP-схемы соответствуют принятому в ai-core TypeBox.

Основные места изменения:

- `foundations/core/packages/collaborator-client/src/`: контракты и вызовы новых RPC; отдельная политика повторов для записей.
- `server/collaborator/src/rpc/methods/`: тонкие обработчики чтения, схемы и пакета правок.
- `server/collaborator/src/`: вызов ядра операций и мост ProseMirror ↔ живой Yjs fragment с настоящим lifecycle сохранения.
- `foundations/core/packages/text-agent/src/operations/`: реализованное общее ядро операций, ссылки, описание схемы и явная политика редактирования.
- `foundations/core/packages/text-agent/src/operations/yjs-references.ts`: реализованный адаптер живых контейнеров через публичные relative positions и mapping снимка.
- `services/ai-bot/ai-tools/`: MCP-инструменты поверх клиента.

Названия новых методов и инструментов ниже — предлагаемый контракт, а не уже существующее API.

## Реализованная основа и текущий статус

Код из приложенного примера адаптирован в `@hcengineering/text-agent`. Ядро принимает ProseMirror `EditorState`, область документа/поля, явную политику и `AgentReferenceSource`. `prepareAgentOperations` возвращает проверенную транзакцию и внутренние координаты целей, не меняя входное состояние. После применения к Yjs `finalizeAgentOperations` выдаёт публичные handles и отпечатки из нового живого снимка. The adapter and operation core belong to `text-agent`; `text` and `text-ydoc` expose no agent operations.

| Часть | Статус | Оставшаяся работа |
| --- | --- | --- |
| Контракты ядра, `getEditorContext` | Реализовано | RPC-контракты и привязка метаданных кастомных расширений |
| Handles, outline, чтение узла, текстовый поиск | Реализованы ядро и Yjs-адаптер; путь остаётся меткой отображения | Ограничение выдачи, клиент, RPC и MCP-инструменты |
| Шесть операций и проверка всего пакета | Реализовано, включая fingerprint удаления | Подключение к живому запросу с авторизацией |

Проверки: 44 теста ядра и 11 тестов Yjs-адаптера; всего 123 теста текстового пакета и 62 теста `text-ydoc` проходят. Проверки типов обоих пакетов проходят. Стенд `run.sh --check-ops`: 14 сценариев, 43 проверки. Он подтверждает проверенные случаи, но не заменяет проверку прав, хранения, клиентского отображения и полного паритета схем.

Описание API ядра, запуск и границы проверки: [MVP ops-слоя](../dev/tiptap-ai-prototype/ops-mvp.md).

## Чтение и схема

Чтение разделяется на описание схемы, outline документа, чтение выбранного узла и поиск. MCP-инструменты: `doc_get_schema`, `doc_outline`, `doc_read_node`, `doc_find`. Запись предоставляет `doc_apply_ops`. Соответствующие методы подключаются к существующему RPC коллаборатора; отдельное пространство HTTP-маршрутов `/agent` не требуется.

Описание схемы сообщает поддерживаемые node/mark types, разрешённые и защищённые атрибуты, операции, ограничения вложенности, inline atoms и служебные marks. Источник — реальные расширения и явная политика редактирования. Атрибуты `id`/`uid` не служат адресами MCP: они могут обозначать внешний документ, файл или комментарий.

Чтение возвращает структуру, текст и ссылки на адресуемые узлы. Marks описываются внутри содержимого; обычное форматирование адресуется через контейнер и текстовый селектор. Существующие идентификаторы специальных marks сохраняются, но универсальная генерация UUID для marks не вводится.

Чтение не создаёт ID и не нормализует документ. Для неизвестного содержимого доступно исходное структурное представление с диагностикой. Запись блокируется с `UNSUPPORTED_SCHEMA`, если документ содержит неизвестные node types, mark types или сериализованные атрибуты. Ничего не отбрасывается молча.

Паритет схем проверяется по сохраняемому содержимому. Сериализованный атрибут нельзя объявить исключительно клиентским, чтобы обойти проверку. Состояние UI должно жить отдельно от содержимого документа.

## Ссылки на узлы

### Handle живого контейнера

`createYjsReferences(document, mapping, scope)` is the shared adapter used by the collaborator and prototype. It walks live `Y.XmlElement` containers in the selected field and binds them to ProseMirror nodes from `initProseMirrorDoc`.

Handles use `encodeHandle(getHandle(element))`: the element creation identity `client.clock` in base36. Document and field are supplied separately. Resolution matches the handle against the current index of that live field; no persistent registry or fallback by position is used.

The adapter excludes deleted containers and verifies XML/ProseMirror type agreement. References are used within one synchronous read/prepare/commit, without capturing or comparing Yjs snapshots. Recreate them after a document change or an `await`. Reading a missing field does not create it. Stored `uid` values do not participate in addressing.

Handles переживают проверенные текстовые правки, marks, обновление атрибутов, вставку соседей и бинарное восстановление Yjs. Удаление или пересоздание контейнера, смена типа с пересозданием и импорт из JSON могут их инвалидировать. Тогда возвращается `STALE_REFERENCE`; агент перечитывает структуру. Подстановка по старому пути, похожему тексту, хэшу или `uid` запрещена.

### Путь и отпечаток

Путь — последовательность индексов дочерних узлов — возвращается для навигации и отображения. Он не используется как адрес записи.

Чтение возвращает `fingerprint` всего канонического JSON узла, привязанный к документу/полю. Канонизация сортирует ключи объектов, сохраняет порядок массивов и включает тип, текст, атрибуты, marks и вложенное содержимое. Серверный адаптер hash должен использовать криптографический алгоритм; на стенде используется SHA-256.

Для `delete_node` обязателен `expectedFingerprint`. Он проверяется до первой операции пакета по начальному снимку. Поэтому собственный `replace_text` перед `delete_node` не нарушает проверку, а изменение marks, атрибутов или вложенных объектов человеком после чтения приводит к `STALE_REFERENCE`. Для остальных операций общей проверки ревизии или совпадения содержимого нет.

Новые узлы получают handles после применения пакета к Yjs, когда существуют реальные контейнеры. `finalizeAgentOperations` проверяет соответствие живого результата подготовленной транзакции и возвращает handles и fingerprints сохранившихся целей либо `deleted: true`.

## Операции MVP

| Операция | Назначение и ограничения |
| --- | --- |
| `insert_node` | Вставить валидный поддеревом узел относительно существующей цели либо в разрешённую позицию родителя |
| `update_attrs` | Изменить только явно разрешённые атрибуты, сохраняя остальные |
| `delete_node` | Удалить выбранный узел вместе с поддеревом при совпадении expectedFingerprint начального состояния |
| `replace_text` | Заменить буквальное совпадение текста внутри указанного контейнера |
| `add_mark` | Применить разрешённый обычный mark к найденному тексту |
| `remove_mark` | Снять указанный обычный mark с найденного текста |

Текстовый селектор ищет точное буквальное совпадение в текущем состоянии контейнера. По умолчанию требуется одно совпадение; несколько дают `AMBIGUOUS_MATCH`. Все совпадения обрабатываются только при явном `all: true`. Поиск может проходить через текстовые фрагменты с разными marks, но не пересекает inline atoms и hard breaks.

Новый текст наследует обычное форматирование начала заменяемого диапазона. Остальное форматирование меняется отдельными операциями. Служебные marks комментариев не входят в обычный API форматирования: их нельзя создавать, снимать или подменять таким способом. Существующие привязки сохраняются для остающегося содержимого; удаление затронутого текста может убрать его anchors.

Явное удаление узла может удалить вложенные изображения, ссылки на объекты и anchors комментариев. Внешние файлы, документы и записи комментариев при этом не удаляются. Операции не меняют содержимое за своими границами.

Предлагаемое ограничение MVP: узел, вставленный текущим пакетом, задаётся сразу целиком; последующие операции над ним выполняются после получения ссылки из ответа. Локальные aliases для новых узлов можно добавить позже.

## Выполнение пакета

1. Проверить токен, workspace, доступ к документу/полю и право записи для текущего запроса. Не полагаться на WebSocket authentication: direct connection его не выполняет.
2. Получить актуальный живой документ, проверить исходное содержимое и совместимость схемы без изменений Yjs.
3. Разрешить handles через живые контейнеры начального состояния и проверить expectedFingerprint всех удалений. В дальнейшем отслеживать цели через mapping транзакций ProseMirror. Это позволяет несколько раз изменить один блок и вставить соседний блок без повторного обращения к ещё не изменённому Yjs mapping.
4. Последовательно выполнить операции на отделённом состоянии ProseMirror. Текстовые совпадения проверяются в состоянии после предыдущих операций. Обращение к уже удалённой цели завершает весь пакет ошибкой.
5. Проверить структуру и допустимость результата без автоматического удаления неизвестных атрибутов или незапрошенного исправления структуры.
6. Применить проверенное изменение к живому fragment через проверенный мост, сохраняя незатронутые Yjs-объекты. Между финальным снимком, подготовкой и применением не должно быть `await`; при невозможности этого условия пакет пересчитывается на актуальном состоянии до записи.
7. Построить новый живой снимок и финализировать результаты с реальными handles, затем завершить существующий цикл сохранения и вернуть подтверждённый ответ.

Ошибки разрешения целей и проверки операций возникают до записи и не должны оставлять частичных изменений. Yjs transaction сама по себе не обеспечивает rollback при исключении. Поэтому безопасность применения — отдельный критерий проверки моста, а не свойство, которое можно получить обёрткой `transact`.

Сбой сохранения после применения не означает откат уже разосланной правки. Ответ различает подтверждённое выполнение, ошибку до применения и неопределённый результат. Один пакет не обещает один шаг пользовательского undo.

Права и авторство принадлежат текущему запросу; их нельзя кэшировать вместе с документом от имени первого пользователя. В первую очередь используем существующий lifecycle Hocuspocus. Отдельный долгоживущий Editor и собственный кэш сессий добавляются только при доказанной необходимости.

## Серверный мост: обязательная проверка до интеграции

Не используем существующий `updateContent` как исполнитель: он пересоздаёт и очищает fragment целиком. Не считаем, что не смонтированный Tiptap Editor с Collaboration автоматически синхронизирует живой документ.

Кандидат для стенда — публичные `initProseMirrorDoc` / `updateYFragment` из установленного `@tiptap/y-tiptap`. Проверка должна доказать работу на реальной общей схеме. Некоторые пути преобразования могут исправлять повреждённые данные и тем самым писать при чтении; перед ними необходима проверка исходной структуры, а тесты должны отслеживать любые Yjs updates.

До прохождения этой проверки нельзя обещать атомарность применения и сохранение привязок. Если мост не удовлетворяет условиям, пересматриваем способ применения до подключения MCP; не заменяем его скрытым полным пересозданием документа.

## Ошибки и повторы

Коды ядра: `FORBIDDEN`, `UNSUPPORTED_SCHEMA`, `INVALID_OPERATION`, `SCHEMA_INVALID`, `POSITION_INVALID`, `STALE_REFERENCE`, `AMBIGUOUS_REF`, `TEXT_NOT_FOUND`, `AMBIGUOUS_MATCH`, `TOO_MANY_OPS`. Серверная интеграция дополнительно должна различать `WRITE_OUTCOME_UNKNOWN` после возможного применения.

Ошибка указывает индекс операции, безопасную диагностику и следующее действие агента. Для неопределённого результата записи следует перечитать документ и решить, нужна ли новая команда. Нельзя автоматически воспроизводить тот же пакет. Существующий цикл повторов `updateMarkup` для новых записей не используется. Чтения можно повторять.

## Фазы исполнения

Каждая фаза заканчивается работающим сценарием через MCP и отдельной ручной проверкой. Задачи внутри фазы выполняются в указанном порядке. Автоматические проверки добавляются вместе с соответствующей функциональностью.

### Фаза 1. Чтение — MVP read-only

**Результат:** агент может узнать схему, просмотреть структуру, прочитать узел и найти содержимое существующего документа. Чтение не меняет документ и не требует предварительной миграции.

1. **Общие контракты и возможности схемы — ядро готово, интеграция остаётся.**
   - Добавить контракты запросов, результатов, ссылок и ошибок в `collaborator-client`.
   - Реализовать `describeSchema` на основе общей схемы и явных метаданных редактирования.
   - Описать возможности кастомных nodes/marks через метаданные `agent` расширений, включая хранение в `addStorage`, где это подходит существующей реализации.
   - Указать разрешённые и защищённые атрибуты, служебные marks и inline atoms. Метаданные выводятся сервером и не сохраняются в содержимом документа.
2. **Адресация узлов — реализована в ядре; проверить в RPC-сценариях.**
   - Use the shared `createYjsReferences` with the live collaborator snapshot mapping; the prototype and integration tests use the same adapter.
   - Проверять область документа/поля, принадлежность живому дереву и соответствие XML/ProseMirror типов. Путь и uid не участвуют в разрешении.
   - Возвращать отпечатки поддеревьев для последующих проверок удаления.
   - Старые документы без UUID должны работать сразу; генерацию ID и backfill не подключать.
3. **Методы чтения в RPC.**
   - Описание схемы.
   - Outline: иерархия адресуемых узлов с типами, кратким текстом и ссылками.
   - Чтение узла: содержимое, marks, атрибуты и ссылки вложенных адресуемых узлов.
   - Поиск: буквальный поиск текста с указанием содержащих его узлов; границы совпадений соответствуют правилам текстовых селекторов.
   - Для выдачи outline, поиска и поддеревьев предусмотреть ограничение размера ответа и явный признак неполной выдачи; неполный результат нельзя выдавать за полный.
   - Проверять права чтения и контекст пользователя до доступа к содержимому.
4. **MCP-инструменты.**
   - `doc_get_schema`, `doc_outline`, `doc_read_node`, `doc_find` поверх `collaborator-client`.
   - Описать срок жизни handles и порядок перечитывания при `STALE_REFERENCE`.
5. **Проверки фазы.**
   - Добавить тест паритета серверной и клиентской схем в существующий CI-процесс проверок.
   - Проверить отсутствие Yjs updates при всех чтениях, включая старые и неподдерживаемые документы.
   - Проверить одинаковые блоки и дубликаты uid, вставки соседей, изменение содержимого, удаление/пересоздание, неизвестные типы и атрибуты, запрет доступа.

**Условие завершения:** через MCP пройден сценарий «схема → outline → поиск → чтение выбранного узла», содержимое до и после чтения совпадает, тест паритета проходит. Неизвестная схема доступна для диагностического чтения без нормализации.

### Фаза 2. Запись — MVP редактирования

**Зависимость:** завершена фаза 1; её ссылки, схема, права и MCP-клиент используются для записи.

**Результат:** агент применяет проверенный пакет адресных правок к живому документу; человек видит результат в редакторе.

1. **Довести проверенный на стенде способ применения до серверной интеграции.**
   - Проверить мост ProseMirror ↔ живой Yjs fragment на настоящей общей схеме и двух репликах.
   - Подтвердить сохранение незатронутого содержимого и привязок, отсутствие скрытой нормализации и полных пересозданий fragment.
   - Проверить ошибки до применения и возможные сбои во время применения/сохранения. Зафиксировать достижимые гарантии до подключения публичной записи.
   - Если мост не проходит проверку, пересмотреть его реализацию до дальнейшей интеграции записи.
2. **Lifecycle документа и текущий пользователь.**
   - Использовать существующие direct connections и lifecycle Hocuspocus; обеспечить закрытие подключений при успехе и ошибке.
   - Организовать последовательное применение пакетов агента для одного документа. Мьютекс не считается блокировкой удалённых пользователей.
   - Если понадобится `DocSession`, ограничить её ответственность владением подключением и выполнением операций; определить TTL, очистку и закрытие. Собственный кэш Editor не является обязательной частью MVP.
   - Проверять право записи до изменения документа и передавать контекст текущего пользователя без кэширования чужих прав или авторства.
3. **Подключить реализованные операции над отделённым состоянием.**
   - `insert_node`, `update_attrs`, `delete_node`, `replace_text`, `add_mark`, `remove_mark`.
   - Разрешать исходные ссылки один раз на старте пакета и отслеживать цели после каждой операции через mapping ProseMirror.
   - Проверять expectedFingerprint удалений на начальном снимке и финализировать публичные handles только после применения к Yjs.
   - Проверять текстовые совпадения, ограничения вложенности, атрибуты и служебные marks; сохранять незатронутое содержимое.
   - Вставляемый узел задаётся целиком. Следующие запросы используют ссылку из ответа; локальные aliases новых узлов откладываются.
4. **Пакет записи в RPC и клиенте.**
   - Проверять весь пакет до применения, возвращать индекс ошибочной операции и структурированную причину.
   - Применять проверенный результат к актуальному живому состоянию согласно правилам раздела «Выполнение пакета».
   - Возвращать актуальные ссылки и явно различать отказ до записи, подтверждённое выполнение и неопределённый результат.
   - Не использовать автоматические повторы существующего `updateMarkup` для новых операций записи.
5. **MCP-инструмент и проверки.**
   - Подключить `doc_apply_ops`.
   - Проверить несколько операций над одним узлом, сдвиги позиций, ошибку последней операции, неоднозначный текст и сохранность служебных marks.
   - Проверить конкурентные правки человека и агента, ошибки доступа, timeout после применения, ошибку сохранения и закрытие подключения.

**Условие завершения:** сценарий «прочитать → применить пакет → перечитать» работает через MCP и виден человеку в редакторе. Ошибка проверки пакета не оставляет изменений. Неопределённый результат не вызывает автоматического повтора. Пройдены относящиеся к записи общие критерии приёмки ниже.

`move_node` остаётся после MVP: сначала отдельная проверка сохранности конкурентных правок и привязок при переносе.

### Фаза 3. Удобство и ревью — после MVP

**Зависимость:** фазы 1–2 завершены. Каждая возможность ниже выполняется отдельной задачей; её включение требует отдельного дизайна и не является условием готовности MVP.

- **Awareness агента.** Показать присутствие и активность агента, определить время жизни и очистку его состояния.
- **Режим предложений и ревью.** Отдельно спроектировать отображение изменений, accept/reject, авторство и поведение при конкурентных правках. Решить, нужна ли сохраняемая метка `aiChange` или другое представление предложений.
- **Расширенные текстовые селекторы.** При необходимости добавить явные диапазоны внутри блока и более точное управление форматированием. Обычные marks и ссылки через текстовый селектор уже входят в фазу 2.
- **Вставка Markdown.** Проверить преобразование в поддерживаемую схему, сохранность кастомных узлов и необходимость отдельных обработчиков. Предварительно показывать ошибку неподдерживаемого содержимого; не терять его молча.
- **Перемещение узлов.** Провести отдельный конкурентный эксперимент и только по его результату определить контракт `move_node`.

**Условие завершения:** задаётся отдельно для выбранной возможности. Общий режим прямых правок MVP сохраняется доступным независимо от внедрения ревью.

## Критерии приёмки

- Чтение и описание схемы не создают Yjs updates, ID или изменений сохраняемого содержимого, включая старые документы без UUID.
- Проверены одинаковые блоки, вложенные списки и таблицы, изображения, ссылки на объекты, hard breaks, обычные и служебные marks, неизвестное содержимое.
- Handle живого контейнера переживает обычное редактирование, вставки соседей и бинарную загрузку. Удалённая или пересозданная цель не подменяется соседним или одинаковым узлом. Дубликаты uid не влияют на адресацию.
- Изменение любого сохраняемого содержимого удаляемого поддерева после чтения вызывает STALE_REFERENCE. Собственные предыдущие операции batch не вызывают ложный отказ удаления.
- Несколько операций одного пакета над исходной целью корректно работают после собственных изменений текста и сдвигов позиций. Ошибка последней операции не применяет первые.
- Поддерживаемые правки сохраняют незатронутое содержимое, атрибуты и привязки. Удаление поддерева не удаляет внешние ресурсы.
- Две реплики сходятся при проверенных конкурентных сценариях; отдельно проверены правки в одном и разных блоках. Сходимость не выдаётся за гарантию сохранения смысла любой устаревшей команды.
- Проверены чужой workspace, read-only/guest, права на целевое поле и смена пользователя при общем живом документе. Отказы происходят до изменения документа.
- Проверены timeout после применения, ошибка сохранения, закрытие direct connection и сохранение авторства. Ни один такой сценарий не запускает автоматический повтор записи.
- Ручная проверка в редакторе подтверждает отображение результата и совместную работу с MCP. Проверки не требуют автоматического запуска сборки или форматирования репозитория.
