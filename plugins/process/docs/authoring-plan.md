# YAML DSL implementation plan

## Single YAML format consolidation

The supported authoring format is the named-block grammar with `version: 2`. The earlier concise version is removed from compilation, serialization, editor defaults and import binding paths. The plans and verification counts below are historical records, not a promise to maintain two formats.

1. [x] Remove the concise compiler, expression parser and exporter; reject unsupported versions explicitly.
2. [x] Use the shared named-block model compiler/exporter and generic slot binder for every YAML definition.
3. [x] Convert risk/review examples and editor starter definitions; update the current authoring reference.
4. [x] Verify compiler/export round trips, resource imports/saves, starter definitions and native risk execution.
5. [x] Run affected package validation and report manual UI checks without automatic builds or formatting.

Verification: 150 shared authoring tests, 38 process resource tests, 10 card resource tests, 133 native execution tests and 5 CLI tests passed. Resource and execution tests resolved the shared process package to its current TypeScript source instead of stale build artifacts. Validation passed for all four affected packages; changed source files passed lint, and card resources Svelte checking passed. No builds, formatting or commits were run. Manual verification remains: after the normal development build, open both editor starter definitions, import/export the converted examples, save an edited process, and check that a version 1 YAML file reports the unsupported version.

## Typed authoring implementation plan

Goal: make the complete DSL suitable for creating processes from this reference, including typed task/computation results and function composition. Preserve every native value on export/import, JSON and both existing YAML versions. Do not change execution semantics, introduce runtime blocks, or guess undocumented operation contracts.

1. [x] **Document the boundary.** Confirm result/context synchronization and expression evaluation against the engine. Record model limitations: required parameters are available, but full parameter types, result cardinality and graph-dependent context availability are not universally declared. Do not infer a parameter schema from a method's object class.
2. [x] **Add named typed results.** Accept an action `results` mapping; generate result identities and process metadata exactly as native synchronization does. Support readable scalar types and full model types, reference/enum/array types, selection constraints and field binding. Reuse short types in fields/slots and generate the attribute slot kind/class from its type. Preserve unusual native result/context properties; continue accepting old result arrays.
3. [x] **Export results without repeated wiring.** Compact only reproducible result contexts. Keep display order, labels, literal values and unknown extensions unchanged. Ensure mixed ordinary outputs and typed results share consistent identities and declaration order.
4. [x] **Add declarative expressions.** Accept `{expr: {from: ..., pipe: [...], reduce: ..., fallback: ...}}` and function-produced sources. Compile registered functions generically, with explicit source reduction versus value transformation. Never evaluate scripts. Export canonical expressions into the same readable form; retain advanced/legacy native strings when necessary for exact round trips.
5. [x] **Strengthen model-driven diagnostics.** Validate named references, types, function roles and required operation parameters where contracts exist. Installed model contracts take precedence over the file catalog. Keep unknown extension parameters supported; preserve future contract metadata in the exported catalog. Add parser-backed locations for semantic errors and a slot-name fallback in the UI. Do not mistake informational metadata for an exhaustive schema.
6. [x] **Provide a complete worked example, formal schema and concise entry point.** Demonstrate tasks with results, computations from those results, and outgoing branches using existing events/predicates. Cover both embedded cards and standalone slots. Document actual engine restrictions and precise manual UI checks in the authoring reference. Keep the implementation history in this plan rather than before the language contract.
7. [x] **Verify integration and regressions.** Test typed task results, computed results, function chains, invalid contracts, literals, future functions and complete real-export round trips. Check new/current process imports and embedded card cloning through existing resource tests. Run relevant tests and no-emit checks without builds, formatting or commits.
8. [x] **Report measured results and remaining limits.** Distinguish compiler/runtime verification from live UI verification. Do not call the DSL universally typed or claim context availability guarantees that the engine/model cannot establish.

Verification: 173 shared authoring tests, 118 process resource tests, 40 card resource tests and 133 native execution tests passed (464 total). TypeScript no-emit checks passed for the shared package and both resource import/export paths. Svelte reported zero errors and 83 existing warnings in 53 files. The three supplied JSON exports passed complete round trips again, including all 312 Test Case module documents, values, references and relative ranked order. The JSON Schema compiled with the existing local Ajv 8 dependency; both v2 examples, their generated exports and the three real exports matched it, and an invalid pipeline was rejected. Temporary audits were removed; no external fixtures or new validator dependency were added to permanent tests. No builds, formatting, commits or deployment were run. `git diff --check` passed.

Native execution checks exercised collected numeric values, Multiply, SetContext, UpdateCard and the classification predicates, including zero and the exact cost boundary. Resource checks exercised new/current process imports with fresh typed result ids and rebinding, plus embedded card cloning with local fields. A regression fixed symbolic field-name/id collisions during cloning, and dynamic task titles no longer become inferred static context labels. Live task completion, editor interaction and workspace saves still require the documented manual UI check; these tests do not claim a live browser run or a fresh-agent benchmark.

Remaining model/engine boundaries: full optional/conditional parameter schemas, function property types, result cardinality, numeric input constraints and graph-dependent result availability are not universally described by the model. CreateToDo in all mode suppresses user results. The existing engine has one active state per execution and a bounded immediate-transition chain. The DSL preserves these behaviors and does not promise parallel joins, aggregation or universal static type safety without verified engine/model contracts.

## Readable outputs and references implementation plan

This change removes repeated context wiring from ordinary v2 authoring. It does not change the execution engine or translate methods individually.

1. [x] **Define explicit reference semantics.** `$slots.name` is the bound field name or model identity; `$card.name` reads a card field (using its attribute slot when declared); `$context.name` reads a published action result. Support nested field selectors, validate slot/context names, and keep advanced native expressions supported. Distinguish literal text from references instead of guessing from parameter names.
2. [x] **Resolve output types through method contracts.** Allow `as: result_name`; resolve `createdContext` through the installed model, or an exported catalog for offline compilation. Missing contracts and methods without a result must report an error. Support explicit class/label/order overrides for existing exported metadata and specialized result classes, without operation-specific mappings.
3. [x] **Generate context wiring.** Generate action context and process context metadata (`action`, `producer`, `index`, `value`). Detect duplicate output names and conflicts with explicit contexts. Preserve existing explicit metadata and task result definitions; no execution migration.
4. [x] **Export readable outputs and references.** Use `as` when its generated data reproduces the native output; retain unusual metadata explicitly. Preserve literal strings and unknown native extension properties, including names colliding with the new syntax. Verify complete native data and order survive round trips.
5. [x] **Connect the installed model to UI validation/import.** Pass the model to shared compilation from the editor, slot discovery and both import routes. Installed contracts take precedence over informational catalog data. Preserve old JSON and YAML behavior.
6. [x] **Update the example and agent reference.** Rewrite approval with named outputs/references and no manual process context map. Document the supported syntax, reference/value distinction, offline requirements and precise errors in this file.
7. [x] **Verify.** Test compiled approval wiring, custom model methods, invalid/missing/duplicate references, literal escaping, full export round trips, slot binding and saving existing processes. Run TypeScript/Svelte checks and relevant tests without builds or formatting; record results.

Verification: 140 shared authoring tests, 116 process resource tests, 39 card resource tests and 128 native execution tests passed. The three supplied JSON exports also passed round trips with output contracts and named references, including the full Test Case module. TypeScript checks passed; Svelte reported zero errors and 83 existing warnings. New/current process saves and embedded card imports were tested with installed method contracts and generated output wiring. No builds, formatting or commits were run. Manual UI verification remains: open approval YAML, bind Approvers/Approved, import a new process, save an edited current process, and inspect its generated result in the visual editor.

## Complete YAML DSL implementation plan

The purpose is agent-friendly authoring from one self-contained reference, not merely changing JSON indentation. The complete v2 DSL is authorized alongside concise v1. Both must be readable authoring formats; native document storage must not become the ordinary YAML syntax. Preserve existing JSON behavior and the runtime. Do not add operation-by-operation translations or migrate active executions. Include a workspace-generated operation catalog with full exports so authors can inspect the actual registered contracts without searching source files. Document small named states as logical blocks and the native expression/reference syntax in this guide.

1. [x] **Define the full model contract.** Add `version: 2`, `kind: card | process`, named model sections and nested process/state/transition/action blocks. Generate document classes, identities, ownership and ranks; shorten built-in operation names. Preserve all document classes, properties, native expressions, contexts, action results, slots and dependent types. Keep concise v1 definitions supported. Unsupported concise exports must use the full representation without omitting data.
2. [x] **Implement shared parsing and serialization.** Reuse safe YAML parsing and diagnostic paths. Validate document identity, duplicate ids and process graph references, without hardcoded operation/type/property allowlists. Keep serialization deterministic and verify that parsing restores every business value and reference, with generated ranks preserving branch priority and display order.
3. [x] **Connect workspace model validation and discovery.** Resolve methods and triggers through the installed model at apply time. Include the installed methods, triggers and functions with their model-defined required parameters, defaults, context types and descriptions in the exported catalog. Accept newly registered operations automatically. Report missing operation ids before any writes; preserve operation parameters without inventing defaults or reinterpretations. The catalog documents capabilities; importing it must not install or redefine operations.
4. [x] **Support every existing slot kind.** Reuse class, association, process and attribute binding controls; validate bindings and `memberOf` against the destination model. Prefill all compatible bindings when editing an existing process. Preserve enum and reference-type constraints.
5. [x] **Resolve references and save full processes.** Create new graph/action/context ids for a new process, retain the selected process identity for Save current, and resolve slots in structural references and native expressions. Preserve literal labels, titles and field values. Replace obsolete graph documents in the existing transaction; retain process owner/rank and report rejected commits.
6. [x] **Integrate card modules and the UI.** Export/import full card models including dependent types, permissions, viewlets, roles, identifiers, mixins and embedded processes through the existing module importer. Allow the same editor to validate and apply either YAML version. Preserve JSON import/export behavior.
7. [x] **Add regression coverage from real exports.** Check the supplied approval process both with and without slots, and the full Test Case module. Verify all business values and relative order survive YAML round trips, all slot kinds bind correctly, action results and context expressions retain consistent references, and future registered operations/properties do not require exporter changes.
8. [x] **Verify and document.** Run targeted tests and TypeScript/Svelte checks without builds or formatting. Document both formats, exact identity/binding behavior and manual export/edit/import checks. Update this checklist with actual results.

Verification: 124 shared authoring tests, 113 process resource tests, 38 card resource tests, and 128 native execution tests passed. The three supplied exports also passed a separate round-trip audit, including the 312-document Test Case module. Checks compare every business value and reference plus relative ranked order, allowing compiler-generated ranks and document regrouping. TypeScript checks passed; Svelte reported zero errors (83 existing warnings in 53 files). No builds or formatting were run. Manual UI verification remains: export a complex process as YAML, edit a named action, save into the current process, import a new copy with slots, and import/export a card module in both formats.


### Implementation plan

Implement the first version in the following order. Keep this checklist updated as work progresses; record any scope change before implementing it.

1. [x] **Freeze the v1 contract and package location.** Define strict `version: 1` / `kind: card` and `kind: process` documents, shared field/slot types, calculation expressions, and explicit states/transitions. Reuse `js-yaml` parsing independently of Unified Format variable substitution. Keep the compiler in the shared process package so both existing import paths can use it.
2. [x] **Implement parsing and diagnostics.** Reject unsupported versions, unknown keys, malformed definitions, unknown operations, and invalid value types with paths identifying the offending YAML property. Do not evaluate JavaScript or silently reinterpret existing Unified Format files.
3. [x] **Implement card modules.** Compile card types, choice enums, editable/defaulted fields, automation-only calculated fields, and embedded process definitions to native model documents. Generate consistent ids and ranks. Resolve symbolic local field keys to generated stored names.
4. [x] **Implement standalone slot templates.** Compile typed attribute slots and the shared process graph to portable process documents with placeholders and `requiredSlots`. Keep destination bindings in the existing process import workflow; do not create destination fields or invent workspace references.
5. [x] **Implement the two verified patterns.** Support numeric conversion and multiplication, ordered conditional cases, and recalculation after input changes for risk assessment. Support field updates, task creation with explicit completion/rollback settings, and waiting for the published task group for the review process. Represent readable blocks with existing states/transitions. Reject any other behavior until its native contract is explicitly supported.
6. [x] **Integrate with existing import paths.** Accept YAML alongside native JSON in card module and process imports. Preserve existing JSON behavior and binding UI. Add file extension support in the responsible file pickers and report YAML compilation errors through the existing error handling. Do not add a separate editor or change execution services.
7. [x] **Add concrete YAML examples and update this guide.** Provide a risk card module and a standalone review process using slots, with exact field/action/expression syntax and manual import instructions. Keep the native JSON examples for comparison. Document supported v1 features and explicit limitations.
8. [x] **Verify the implementation.** Test generated document references, parameter contracts, portable slots, invalid input diagnostics, calculation dependencies/cycles, and all 25 risk combinations using native expression resolution. Check TypeScript/Svelte diagnostics where available, run appropriate tests and non-build validation, and review the diff. Do not run builds, formatters, commits, or deployment commands automatically. Ask the user to verify imports and behavior manually.

Verification completed: 46 tests in the process package, 86 in process resources, 31 in card resources, and 32 native risk execution tests, including all 25 probability/severity combinations. TypeScript checks with `--noEmit` passed. Svelte checking found no errors and 61 warnings in the checked components and their imports. The language-server diagnostics tool was unavailable, so CLI checks used source mappings for the new shared API without rebuilding packages. `git diff --check` passed. UI import and live process execution still require the manual checks above.

The initial delivery implemented concise YAML compilation and import. The first follow-up added export format selection and a text-based YAML editor with validation and process saving. The full model extension above adds existing approval, subprocess and other native features without new runtime operations. MCP, new runtime entities, arbitrary scripts and changes to active execution handling remain outside this delivery.

### Follow-up plan: export formats and UI authoring

This extends the completed import delivery. Keep JSON compatibility and the existing runtime. Do not add MCP integration or replace the visual process editor.

1. [x] **Confirm the existing export and UI contracts.** Reuse the card module and process exporters, including process slot handling. Inspect the shared UI catalog and existing multiline editors. Keep the new authoring dialog accessible from card type settings and process settings without introducing a resources-package dependency cycle.
2. [x] **Implement strict native-to-YAML conversion.** Read the actual exported model, reconstruct supported field types, slots, states, triggers, ordered actions, and task contexts. Preserve calculation expressions through a verified reverse mapping. Reject unsupported operations, metadata, relationships, permissions, and graph shapes explicitly; never omit them. Validate exported YAML through the same compiler before offering it for download.
3. [x] **Verify round trips and slot portability.** Cover risk calculations, review tasks, embedded processes, and standalone templates. Check that selected choice values remain available after enum ids change, branch/action order and completion/rollback settings survive, and unsupported configurations fail with a useful path. Downloaded DSL remains a portable creation template. The editor may save it into the explicitly selected current process without putting workspace ids in the YAML.
4. [x] **Add export format selection.** Offer JSON and YAML in the existing card and process export controls. Preserve JSON with/without slots options. YAML uses the DSL and typed slots for standalone processes. Choose matching file extensions and MIME types, revoke download URLs, and show conversion errors in the existing notification system.
5. [x] **Expose authoring diagnostics for UI use.** Reuse compiler validation for YAML syntax, version/kind, unknown properties, expressions, references, and graph constraints. Include parser line/column when available and the semantic property path. Validation must not write to the workspace or enable import for an invalid document.
6. [x] **Implement a focused YAML authoring dialog.** Compose existing dialog, text editor, buttons, and notices. 7. [x] **Integrate UI actions and localization.** Add a YAML editor action alongside existing card/process import and export controls, and allow opening a supported existing export in the editor. Define resource/string ids once in the responsible plugin and add English entries to every supported locale. Preserve the visual editor and avoid shared-component style overrides.
8. [x] **Verify and document the delivery.** Run meaningful reverse-conversion, diagnostic, and import tests; check modified TypeScript/Svelte without building or formatting; review compatibility and the diff. Update this guide with exact supported export behavior, editor entry points, and manual verification steps. State any remaining limitation explicitly.
